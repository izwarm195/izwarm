# 一、BEATs 具体是怎么用的？使用了完整的前向推理吗？

根据论文描述，BEATs 的使用方式如下：

1. **模型与状态**：使用 **BEATs-iter 3+** 作为音频编码器，参数量约 90 M，**参数冻结**，不参与训练/微调。

2. **输入与输出**：输入 **10 秒波形**，BEATs 将其转换为 **768 维的 token 嵌入序列**，输出速率为 **50 tokens/s**，因此总长度为 **500 个 token**。也就是说，保留的是帧级/时序 token 序列，而不是只取一个全局池化向量。

3. **是否完整前向推理**：按论文描述，BEATs 是作为冻结特征提取器对整段 10 秒音频做**完整前向编码**，得到 500×768 的 token 序列；论文没有提到裁剪层、跳过层或只使用部分 BEATs。它不使用 BEATs 的分类头，只取编码器输出的 token embeddings。前向计算会进行，但梯度不会回传到 BEATs。

4. **后续处理**：BEATs 输出的 500 个 token 先通过**时间平均池化**下采样到 **100 个 token**，再经过 **3 层 SwiGLU MLP** 投影到 Qwen 2.5-0.5 B 的输入空间，作为 LLM 的音频 token。

   因此，可以概括为：**BEATs 以冻结方式对 10 秒音频做完整前向编码，输出 500 个 768 维时序 token；随后池化到 100 个 token，再经 MLP 投影送入 LLM。** 论文没有使用 BEATs 的完整分类流程，而是把它当作冻结的音频特征编码器。

# 二、在 [TMUSystem](/notes/text-to-audio/papers/tmusystem/the-tmu-system-for-the-xacle-challenge-training-large-audio-language-models-with-clap-pseudo-labels/) 的前向中，BEATs具体到哪？

结合你提供的图片和论文内容，论文中对 BEATs 的使用**具体到图片中的“ViT 输出表示：\(B \times T \times 768\)”这一步**，并且**忽略了图片最下方的 MeanPool 和线性分类器**。

详细对应关系如下：

### 1. 完全对齐的部分（从头到 ViT 输出）
*   **输入**：\(10\) 秒音频，对应 \(16000 \times 10 = 160000\) 个采样点。
*   **Mel 特征与 Patch 切分**：按照图中的计算，10 秒音频的 \(F \approx 1000\)，时间 patch 数 \([1000/16] = 63\)，频率 patch 数为 8，总 patch 序列长度 \(T \approx 8 \times 63 = 504\)。
*   **ViT 输出表示**：得到形状为 **\(B \times 504 \times 768\)** 的张量。
*   **论文描述**：“converts a 10 s waveform into a sequence of 768-dimensional token embeddings at 50 tokens/s (500 tokens total)”。这正好对应图中的 \(504\)（论文取整为 \(500\)）个 768 维的 token。并且图片中强调“推理时不打 75% mask，喂完整 patch 序列”，这与论文中使用冻结的 BEATs 做**完整前向推理（Full Forward）**完全一致。

### 2. 论文中发生的分叉（不用图片下半部分）
图片展示的是 BEATs 用于**音频分类任务**的标准流程（先 `MeanPool` 变成 \(B \times 768\)，再通过线性层输出 \(B \times C\) 的类别概率）。

**而在这篇 XACLE 论文中，作者并没有走图片的全局池化和分类器：**
*   **没有做全局 MeanPool**：论文保留了时序信息，没有把 500 个 token 池化成一个 \(768\) 维的向量。
*   **没有使用线性分类器**：不需要输出 \(B \times C\) 的类别概率。
*   **作者自己设计了后续流程**：
  1. 取了这 500 个 token（即图中的 \(504 \times 768\)）。
  2. 执行了**时间平均池化（Temporal average pooling）**，将 500 个 token 降采样到 **100 个 token**（论文原文：“downsampled to 100 tokens via temporal average pooling”）。
  3. 将这 100 个 token 送入了 3 层 MLP 投影层，然后再送入大语言模型（Qwen 2.5）。

### 总结
在这张图中，论文只截取了**从“原始波形”到“ViT 输出表示 \(B \times T \times 768\)”** 这一段。图中的 504 个 patch 对应论文中的 500 个 token，后续的处理完全脱离了分类任务的范式，转入了大语言模型（LALM）的对齐打分范式。

# 三、LLM 在这里的主要作用是什么？
在这篇论文中，LLM（Qwen 2.5-0.5 B-Instruct）是系统的**核心大脑**，主要扮演三个关键角色：**多模态语义融合器**、**任务特征提取器**，以及**对齐分数回归器**。

具体来说，它的主要作用体现在以下几个方面：

### 1. 多模态语义深度融合（Fusion）
BEATs 只能提取声音的声学特征（“是什么声音”），文本 Tokenizer 只能提取词法特征（“文字字面意思”）。LLM 的作用是将这两者在高维语义空间中进行对齐和交互。
*   输入给 LLM 的序列格式是：`文本 Tokens ... <|AUDIO_START|> 音频 Tokens ... <|AUDIO_END|> <|SCORE|>`。
*   由于 Qwen 2.5 是纯解码器架构（具备因果注意力 Causal Attention），文本作为前缀（Prefix），音频 Token 作为后续上下文，LLM 通过自注意力机制（Self-Attention）计算文本与音频片段之间的细粒度语义匹配度（例如，判断“a machine beeps continuously”是否准确描述了这段机械提示音）。

### 2. 通过特殊 Token 提取任务表征（`<|SCORE|>`）
为了得到一个整体的“分数”，作者没有像传统分类任务那样使用全局池化（MeanPool），也没有简单地取最后一个文本 Token 的隐藏状态，而是**在词表中专门新增了一个 `<|SCORE|>` Token，放在整个序列的最末端**。
*   LLM 的作用就是利用因果注意力机制，把前面所有文本和音频的信息都汇聚、压缩到这个 `<|SCORE|>` 对应的隐藏层状态中（维度为 896）。
*   这个设计类似于 BERT 中的 `[CLS]` 标签，但因为用的是自回归 LLM，所以放在句末。论文提到，这种操作比直接用最后一个 token 的效果更好。

### 3. 从“文本生成”向“评分回归”的范式转换
LLM 在这里不再仅仅是一个聊天机器人或文本生成器，而是被改造成了一个**音频-文本对齐的奖励模型（Reward Model）**：
*   **Stage 1（AAC 预训练）**：此时 LLM 发挥的是传统的**生成能力**，学习根据音频输入生成音频描述（Caption），以理解音频内容。
*   **Stage 2 & 3（打分微调）**：在 LLM 头顶接了一个线性层（Score Head）。此时 LLM 的作用变成了**特征编码与回归**。它把 `<|SCORE|>` 位置的隐藏状态（896 维）映射为一个标量分数。

### 总结
如果说 BEATs 负责听懂“发生了什么”，文本 Tokenizer 负责看懂“写了什么”，那么 **LLM 的作用就是作为一个裁判（Judge），把听到的、看到的信息放在一起做阅读理解，并最终在其内部生成一个代表它们匹配程度的“打分特征”**。

论文中也证明了这一点：采用 LLM 架构（LALM）的模型，在验证集上的 SRCC（0.674）甚至超越了作为“老师”的 CLAP 模型（0.602），说明 LLM 在处理这种复杂的跨模态语义对齐判断时，具有架构上的优势。

# 四、LLM 是冻结的吗？解释一下三段训练
### 一、 LLM 是冻结的吗？

**不是冻结的。** 

在这篇论文中，**只有音频编码器（BEATs）被冻结了**（见表 1 中的“frozen”标注，以及 2.1 节的描述），参数量固定为 90 M，不参与梯度更新。

而 **LLM（Qwen 2.5-0.5 B，494 M 参数）以及音频投影层（MLP）、打分头（Score Head）都是参与训练的**。从第 3 节“Experiments”给出的学习率（Stage 1 和 2 为 \(1 e-5\)，Stage 3 为 \(6.2 e-6\)）也可以确认，LLM 的参数在不断更新。

---

### 二、 三段训练（Three-stage Training Pipeline）详细解释

作者设计这套三段式流水线，核心目的是**循序渐进地让模型从“听懂声音”过渡到“学会打分”**。

#### **Stage 1：AAC 预训练（自动音频描述预训练）**
*   **目标**：多模态对齐（让 LLM 认识音频 Token），建立“听觉”到“语言”的映射。
*   **数据**：约 273 K 样本（AudioCaps + AudioSetCaps 子集）。
*   **训练组件**：音频投影层（MLP） + LLM。
*   **任务**：给模型输入一段音频，让 LLM 生成对应的文字描述（Automated Audio Captioning）。
*   **结果**：在这个阶段结束后，模型具备了较强的音频理解能力。**但实验发现，这个阶段对最终的打分任务并非不可或缺**（后文会提）。

#### **Stage 2：CLAP 伪标签预训练（弱监督学习）**
*   **目标**：让模型从“生成文字”转向“判断匹配度（回归打分）”。
*   **数据构造（关键点）**：
  *   Stage 1 的数据全是“匹配”的音频-文本对，缺乏“不匹配”的负样本，模型无法学会区分好坏。
  *   作者通过**负采样**（把不同样本的音频和文本互换）合成了大量低分对。
  *   数据量从 273 K 暴增到约 **1,064 K**。
*   **标签来源**：使用预训练好的 CLAP 模型（HumanCLAP-M 2 D）为这 106 万条数据打“伪标签（Pseudo-Labels）”。
*   **训练组件**：加入 Score Head，训练 LLM + 投影层 + Score Head。
*   **损失函数**：**ListNet**。因为这是一个打分排序任务（看 SRCC 指标），作者没有用均方误差（MSE），而是用 ListNet 直接优化排序关系。
*   **结果**：这是**性能提升最大的主力阶段**。模型学会了对齐打分，甚至超越了它的“老师”（在验证集上 SRCC 达到 0.598，而老师 CLAP 是 0.602）。

#### **Stage 3：XACLE 微调（目标域适配）**
*   **目标**：让模型适应 XACLE 挑战赛的特定评分分布（人类主观对齐分数）。
*   **数据**：XACLE 官方训练集（仅 7.5 K 样本）。
*   **数据增强**：由于数据量太小，使用 **SpecAugment**（频域掩码 15、时域掩码 30）防止过拟合。
*   **训练组件**：全模型微调（除了冻结的 BEATs）。
*   **损失函数**：依然是 ListNet。
*   **结果**：将前两阶段学到的“通用对齐能力”适配到了 XACLE 具体的评分标准上，验证集 SRCC 进一步提升至 **0.674**。

  ---

### 💡 论文得出的重要结论（非常反直觉）

作者通过消融实验发现：**Stage 1（AAC 预训练）实际上是有害/无用的**。
*   他们做了一个“无 AAC 预训练”的对照实验（直接从 Stage 2 开始训练），结果验证集 SRCC 为 **0.669**，测试集 SRCC 为 **0.626**。
*   而跑了完整三阶段（含 Stage 1）的测试集 SRCC 是 **0.625**。
*   **原因分析**：生成任务（AAC）和判别任务（打分）存在**任务不匹配（Task Mismatch）**。模型学会生成 caption 后，反而不利于它专注于判断对齐程度；甚至作者发现，训练过打分任务后，模型会丧失生成 caption 的能力。

  **最终策略**：在提交测试集时，作者将“完整三阶段模型”和“跳过 Stage 1（仅 Stage 2+3）的模型”的预测结果进行了**秩平均集成（Rank Averaging）**，抵消了两者的误差，拿到了最好的测试集成绩 **SRCC 0.632**，夺得季军。

# 五、这里使用 AudioCaps 预训练 LLM 吗，规则说明，模型只能用训练集训练，而白名单中有 AudioCaps，这是不是意味着子模块可以拿来用。

**是的，你的理解完全正确。** 

论文中明确使用了 **AudioCaps**（以及 AudioSetCaps 的子集）来进行第一阶段的预训练。如果比赛规则声明“只能使用官方训练集训练，但白名单中包含了 AudioCaps 等公开数据集”，这就意味着**官方允许参赛者使用这些白名单中的外部数据集来预训练或微调模型的子模块**。

结合论文内容和比赛规则，可以从以下几个方面来理解：

### 1. 论文中如何使用 AudioCaps？
在 **Stage 1（AAC 预训练）** 中，作者使用了 AudioCaps 和 AudioSetCaps 的子集约 **273 K 样本**，训练音频投影层（MLP）和 LLM，任务是“自动音频描述（AAC）”。
在 **Stage 2（CLAP 伪标签预训练）** 中，作者基于这些外部数据，通过负采样将数据扩充到了 **1,064 K**，用来训练模型的打分能力。
最后在 **Stage 3**，才使用 XACLE 官方提供的 7.5 K 训练集进行目标域微调。

### 2. 为什么白名单允许使用子模块？
XACLE 挑战赛提供的官方训练集非常小（只有 7.5 K），如果仅用这 7.5 K 数据从头训练大模型（如 Qwen 2.5 + BEATs，近 600 M 参数），几乎必然会导致严重的过拟合。
因此，比赛白名单机制的核心目的是：**允许参赛者利用开源的大规模数据集（如 AudioCaps）来预训练或初始化子模块（如 LLM、音频编码器、投影层），从而获得一个具备通用音频理解能力的“基座模型”，然后再用官方比赛数据去适配具体任务。**

### 3. “子模块拿来用”的合规性与策略
在当前的 AI 竞赛中（特别是多模态大模型领域），这通常被称为 **“External Data Pretraining + Target Data Fine-tuning”** 范式。
*   **合规性**：只要白名单里列出了 AudioCaps，用它来训练投影层或 LLM 就完全符合规则。
*   **红线**：绝不能使用白名单之外的数据，也绝不能把测试集的数据混入预训练或伪标签的生成中。
*   **作者的巧妙之处**：作者用外部数据（AudioCaps）训练了 Stage 1 和 Stage 2，只用了 7.5 K 官方数据做最后的“冲刺微调”（Stage 3）。

### 4. 一个有趣的反差（根据论文结论）
虽然规则允许用 AudioCaps，但论文的实验结果非常具有戏剧性：**Stage 1（用 AudioCaps 训练生成任务）其实对最终的打分任务帮助不大，甚至可能因为“任务不匹配”带来负面影响。**
作者发现，直接跳过 Stage 1，仅用外部数据做 Stage 2（伪标签打分预训练），效果反而更好（验证集 0.669 vs 0.674；测试集 0.626 vs 0.625）。
最终作者甚至把“完整三阶段”和“跳过 AAC 预训练”的两个模型做了**集成（Ensemble）**，才拿到了最好的成绩（SRCC 0.632）。

**总结**：白名单里有 AudioCaps，**不仅意味着子模块可以拿来用，而且鼓励你用它来扩大预训练数据量，以解决官方训练集太小的问题**。只不过这篇论文通过实验证明了，在音频-文本对齐打分这个具体任务上，用 AudioCaps 做生成式预训练，不如直接用 CLAP 伪标签做判别式预训练有效。
