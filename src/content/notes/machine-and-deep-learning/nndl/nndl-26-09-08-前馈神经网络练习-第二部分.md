——用 PyTorch autograd 重做两层 MLP：小批量梯度下降 + 多分类交叉熵 + 鸢尾花三分类

承接 [NNDL 26-09-08 前馈神经网络练习（第一部分）](/notes/machine-and-deep-learning/nndl/nndl-26-09-08-前馈神经网络练习-第一部分/)：上一部分用 `Op` 类手写两层 MLP，自己推导并实现每一层的反向传播；这一部分**把求导交给 PyTorch autograd**，把全批量 GD 换成**小批量（mini-batch）**，损失从二分类 BCE 换成**多分类交叉熵 + softmax**，数据从 `make_moons` 换成 **Iris 三分类**。练习目标：分清"框架接管了什么、自己还必须管什么"，并亲手复现**过拟合的 U 形曲线**。

# 一、公式总结

**记号**：批量 $\boldsymbol X\in\mathbb R^{N\times M}$（$M=4$ 个特征）、隐藏层宽度 $H=16$、类别数 $C=3$。层标 $^{(l)}$ 同第一部分：$(1)$=隐藏层、$(2)$=输出层。损失记 $\mathcal R$；$\delta\boldsymbol A=\partial\mathcal R/\partial\boldsymbol A$ 为上游传来的梯度。

**前向**（隐藏层激活为 Logistic，输出层是 softmax 概率）：

$$
\boldsymbol Z^{(1)}=\boldsymbol X\boldsymbol W^{(1)}+\boldsymbol b^{(1)},\qquad \boldsymbol A^{(1)}=\sigma\big(\boldsymbol Z^{(1)}\big),\qquad \boldsymbol Z^{(2)}=\boldsymbol A^{(1)}\boldsymbol W^{(2)}+\boldsymbol b^{(2)}
$$

$$
\hat y_{nc}=\frac{\exp\big(z^{(2)}_{nc}\big)}{\sum_{c'=1}^{C}\exp\big(z^{(2)}_{nc'}\big)}
$$

> 代码里 `forward` **返回的是 $\boldsymbol Z^{(2)}$（logits），不是 $\hat{\boldsymbol Y}$**：`nn.CrossEntropyLoss` 内部自己带 `log_softmax`，喂概率进去等于算了两遍。要画概率图时得自己补一次 `softmax`（图 2 的 `probs_std` 就是干这个的）。

**损失**（多分类交叉熵 = 正确类别预测概率的负对数均值，是第一部分二分类 BCE 的推广）：

$$
\mathcal R=-\frac{1}{N}\sum_{n=1}^{N}\log \hat y_{n,y_n}
$$

**① softmax + 交叉熵的合成梯度**（对比第一部分要分两步走）：

$$
\delta\boldsymbol Z^{(2)}=\frac{\partial\mathcal R}{\partial\boldsymbol Z^{(2)}}=\frac{1}{N}\Big(\hat{\boldsymbol Y}-\boldsymbol Y_{\text{one-hot}}\Big)
$$

> 第一部分里"① 损失对输出求导"+"② sigmoid 的逐元素门"是两步；这里 softmax 与 CE 合并后，梯度直接就是"**预测减标签**"，干净得不像话。

**② 隐藏层激活反向**（第一部分 ②，现在整段由 autograd 完成）：

$$
\delta\boldsymbol Z^{(1)}=\boldsymbol A^{(1)}\odot\big(1-\boldsymbol A^{(1)}\big)\odot\delta\boldsymbol A^{(1)}
$$

**③ 线性层反向**（第一部分 ③，注意参数梯度的转置方向）：

$$
\delta\boldsymbol W=\boldsymbol X^{\mathsf T}\delta\boldsymbol Z,\qquad \delta\boldsymbol b=\boldsymbol 1^{\mathsf T}\delta\boldsymbol Z
$$

**④ 小批量更新**（对比第一部分的 ⑤ 全批量；$B=16$，一个 epoch 更新 $N/B$ 次，$N=105$ 时约 7 次）：

$$
\boldsymbol\theta\leftarrow\boldsymbol\theta-\eta\cdot\frac{1}{B}\sum_{n\in\mathcal B}\frac{\partial\mathcal R_n}{\partial\boldsymbol\theta}
$$

**⑤ autograd 到底做了什么**：前向时框架把每个算子记进计算图；`loss.backward()` 沿图**逆序**调用各算子的反向函数，把 $\partial\mathcal R/\partial\theta$ **累加**到 `param.grad`（是 `+=` 不是 `=`）。所以三步的顺序是硬约束：

$$
\texttt{optimizer.zero\_grad()}\ \Longrightarrow\ \texttt{loss.backward()}\ \Longrightarrow\ \texttt{optimizer.step()}
$$

> 记忆点：**忘记 `zero_grad()` = 梯度跨 batch 累加**，等效于"学习率越来越大且方向是历史平均"；这和第一部分"BCE 反向少乘 $1/N$ → 梯度整体放大 N 倍"是同一类坑，只是这次是框架帮着踩的。

**⑥ 手写 vs autograd 对照**（同一套数学，两种实现）：

| 环节 | 第一部分（手写 Op） | 第二部分（autograd） |
|---|---|---|
| 前向 | 手工串 `fc → Logistic → fc → Logistic` | `fc1 → sigmoid → fc2` |
| 存中间量 | 每层自己存 `self.inputs` / `self.outputs` | 计算图自动记录，不用管 |
| 反向 | 自己写每个算子的 `backward`，按**逆序**手工调用 | 一句 `loss.backward()` |
| 参数 / 梯度 | `params` / `grads` 两个 dict | `nn.Parameter` + `.grad` |
| 更新 | `BatchGD.step()` 遍历 dict | `optim.Adam(...).step()` |
| 优化器 | 纯 SGD | Adam（一阶动量 + 二阶矩自适应） |
| 批量 | 全批量（一次喂完 799 条） | mini-batch（`DataLoader`，$B=16$） |
| 损失 | 二分类 BCE，输出过 sigmoid | 多分类 CE，输出 **logits** |

## 2.2 模型定义：`MLP`

```python
# MLP with torch
class MLP(nn.Module):
    def __init__(self,input_size=4,hidden_size=16,output_size=3):
        super().__init__()
        self.fc1 = nn.Linear(input_size,hidden_size)
        self.fc2 = nn.Linear(hidden_size,output_size)
        self.ac = torch.sigmoid

    def forward(self,inputs):
        z1 = self.fc1(inputs)
        a1 = self.ac(z1)
        z2 = self.fc2(a1)
        return z2
```

> `forward` 必须返回 `z2`（logits）。返回 `a1` 就是第三部分坑 3：`CrossEntropyLoss` 会把 16 维隐藏层激活当成 16 分类，`fc2` 连计算图都进不去（`grad is None`），而且**完全不报错**。

## 2.3 训练骨架：`Runner` 类

> 下面这版已经修掉了第三部分的坑 4 与坑 5：损失与指标都**按样本数加权**（`* y.size(0)`），并且补上了 `Train_score` 的统计——所以 `history` 里的 train / dev 四条曲线口径一致，可以直接叠在一张图上比。

```python
# runner
class Runner():
    def __init__(self,model,optimizer,loss_fn,metric):
        self.model = model
        self.optimizer = optimizer
        self.loss_fn = loss_fn
        self.metric = metric
        self.history = {
            'Train_score':[], 'Train_loss':[],
            'Dev_score':[], 'Dev_loss':[]
        }

    def train(self,train_loader,dev_loader,num_epochs):
        for epoch in range(num_epochs):
            self.model.train()
            running,running_score,n = 0.,0.,0
            for batch in train_loader:
                *inputs , y = tuple(t for t in batch)
                self.optimizer.zero_grad()
                out = self.model(*inputs)
                loss = self.loss_fn(out,y)
                loss.backward()
                self.optimizer.step()
                running += loss.item() * y.size(0)
                # 顺便统计训练集指标：与 evaluate() 一样按样本数加权
                running_score += self.metric(out.detach(),y) * y.size(0)
                n += y.size(0)
            train_loss = running / n
            self.history['Train_loss'].append(train_loss)
            self.history['Train_score'].append(running_score / n)
            dev_loss,dev_score = self.evaluate(dev_loader)
            self.history['Dev_loss'].append(dev_loss)
            self.history['Dev_score'].append(dev_score)

    @torch.no_grad()
    def evaluate(self,loader):
        self.model.eval()
        loss , score, n = 0.,0.,0
        for x,y in loader:
            out = self.model(x)
            loss += self.loss_fn(out,y).item() * x.size(0)
            n += x.size(0)
            score += self.metric(out,y) * x.size(0)
        dev_loss = loss / n
        dev_score = score / n
        return dev_loss,dev_score
```

**逐段读**：`*inputs , y = ...` 是"最后一个元素是标签、其余全是输入"的通用解包（`*` 在赋值处**收集**，在 `self.model(*inputs)` 处**展开**，一收一放）；`zero_grad → backward → step` 的顺序不可颠倒；`running` 先乘 `y.size(0)` 再累加、最后除以 `n`，得到的是**按样本加权的平均损失**——如果只累加 `loss.item()` 却除以样本数，train_loss 会被缩小 `batch_size` 倍（第三部分坑 4 实测比值 0.0591 ≈ 1/16）。两个循环里的指标都乘 `x.size(0)`，是为了让 train / dev 口径一致、最后一批不满时也不偏袒小 batch。

# 三、踩坑记录——出现的错误逐个分析

## A. 数据 / 划分级

1. **`perm` 算了却没用**（漏写 `X, y = X[perm], y[perm]`）
   - 现象：`Dev_score` **恒为 0.0**，500 轮一条水平线贴在 0 上，`Dev_loss` 却在动。
   - 原因：`load_iris` 的标签是**按类别排好序**的（50 个 0、50 个 1、50 个 2）。用顺序切片 `X[:105]` / `X[105:150]`，train 拿到 `[50, 50, 5]`，**dev 的 45 条全是 virginica**。此时 accuracy 衡量的不是"三分类正确率"，而是"输出 argmax 命中第 2 类的比例"——一个只有 0 / 1 两个取值的单类指标。
   - 修正：`X, y = X[perm], y[perm]` 放在划分**之前**。
   - 教训：**`DataLoader(shuffle=True)` 只打乱 batch 顺序，救不了划分错误**。任何"按比例切片"之前都要先确认数据是不是按标签排序；分类任务的 dev 集必须**分层**，否则指标可能连"多数类基线"都不如。

2. **没有留 test 集**：`tr + dv = 105 + 45 = 150`，全用完了。想报告最终性能必须重新划分（7:2:1）或做交叉验证。

## B. 维度 / 张量级（不崩但错，最难发现）

3. **`forward` 返回的是 `a1`，不是 `z2`**
   - 现象：`model(x).shape ** (16, 16)`，**没有任何报错**，但 accuracy 几乎全错。
   - 原因：`nn.CrossEntropyLoss()` 只要求"输入第 0 维长度 ** 标签长度"，16 维输出配 0..2 的标签**完全合法**——它把隐藏层激活当成 **16 分类**的 logits 在算交叉熵。`accuracy` 又对 16 维做 argmax（取值 0..15）去和 0..2 比，自然全错。
   - 更致命的是：**`fc2` 根本没进计算图**。实测 `model.fc2.weight.grad is None`，训练前后 `fc2` 权重变化量为 **0.0**——最后一层永远是随机初始化，模型"看起来在训练"其实只有 `fc1` 在动。
   - 修正：`return z2`。
   - 教训：**不报错的 bug 最贵**。两个廉价自检手法：① 打印 `model(x).shape`，确认最后一维等于类别数；② `loss.backward()` 之后遍历 `model.parameters()` 看 `p.grad is None`——只要有 `None`，就说明那个参数压根没参与 loss。

4. **`running += loss.item()`，最后却除以 `n`（样本数）**
   - 现象：train_loss 与 dev_loss 差一个量级（实测比值 **0.0591 ≈ 1/16 = 1/batch_size**）。
   - 原因：累加的是**每个 batch 的平均损失**，分母却是**样本总数**，等于把 train_loss 缩小了 batch_size 倍。而 `evaluate` 里 dev 侧是按 `loss * x.size(0)` 正确加权的，两条曲线口径完全不一致。
   - 修正：`running += loss.item() * y.size(0)`（先乘再除 = 按样本加权），或把分母改成 `len(train_loader)`。
   - 教训：**"乘 batch size 再除以样本数"是加权平均的正确写法**；只按 batch 求平均时，最后一批不满会让小 batch 获得过大权重，train / dev 口径也对不齐。

## C. 工程 / 自检级

5. **`history` 里声明了 `Train_score` 却从未写入**：`train()` 只 append 了 `Train_loss`，train 侧的 metric 根本没算（实测 `len(history['Train_score']) == 0`）。图 2 左列两条曲线要成对出现，缺 train 侧就看不出泛化 gap。

# 四、思考：dev_loss 为什么会回升（附 12 组对照实验）

**现象**：训练到某个 epoch 之后，`Train_loss` 还在往下走，`Dev_loss` 却掉头向上——曲线是个 U 形。

**实验**（其余完全同 notebook：隐藏层 16、batch 16、`Adam`、同一套数据划分；只改学习率、轮数和随机种子，各 3 个种子）：

| 学习率 | 轮数 | 种子 0 | 种子 1 | 种子 2 | 末轮 train_loss |
|---|---|---|---|---|---|
| 0.003 | 200 | +0.0000 | +0.0000 | +0.0015 | 0.079 – 0.117 |
| 0.003 | 1000 | +0.0064 | +0.0000 | +0.0754 | 0.013 – 0.063 |
| 0.1 | 200 | +0.0129 | +0.0413 | +0.1878 | 0.006 – 0.053 |
| 0.1 | 1000 | +0.2582 | +0.3072 | **+0.8416** | **0.0000 – 0.027** |

（表中数字 = 末轮 dev_loss − 该次训练 dev_loss 的最低点）

**1) 这是过拟合，不是 bug——容量 > 数据量。**
隐藏层 16 → 参数量 $4\times16+16 + 16\times3+3 = 131$ 个，而训练样本只有 **105** 个（$150\times70\%$）。131 > 105 意味着**模型有能力把训练集完整背下来**。表里 lr=0.1 那一行 `train_loss` 压到 0.0000 就是"记住了"的铁证；dev_loss 的回升幅度随"背得有多狠"单调增大。

**2) 学习率决定"走多远"，因而决定回升幅度。**
同样 1000 轮，lr=0.003 的回升是 **+0.000 ~ +0.075**，lr=0.1 是 **+0.258 ~ +0.842**——差了一个数量级。大 lr 让权重范数迅速膨胀，几十轮就把训练集压到零损失，之后全是多余的"记忆加深"；小 lr 走得慢，同样的轮数根本到不了那个区域。**所以"调小学习率"不只是防震荡，它同样在抑制过拟合的严重程度。**

**3) 为什么 dev_loss 涨而 dev_acc 常常不动（甚至还是 1.0）。**
交叉熵对"过度自信"敏感。继续训练时模型把训练点的 logit 幅度越推越大（train loss 因此下跌），但对**恰好落在边界另一侧的 dev 点**，错得越自信、CE 惩罚越大。快照数据：某个划分下 dev_acc 只从 0.956 掉到 0.933（差 1 个样本），dev_loss 却涨了 **0.33**。→ **看 loss 比看 accuracy 更早发现过拟合。**

**4) 加剧因素（都不是 bug，但决定曲线形状）。**
- 无 `weight_decay`、无 dropout：除了损失本身，没有任何东西约束权重范数。
- 轮数给太多：最低点常常出现在远早于末轮的位置。
- **dev 只有 45 条**，指标是离散的（accuracy 只有 46 个可能取值）；加上划分没有固定随机种子，每次重跑划分都不一样。**"回升多少"本身是抽签结果，不要当定量结论。**

  **5) 结论：U 形曲线正是"早停 / 保存 dev 最优模型"存在的理由。**
  当前 `Runner` 只往 `history` 里 append，从不比较、从不保存，所以训练结束时拿到的是**最后一个 epoch 的模型**——上面 lr=0.1 / 1000 轮那组里，末轮模型在验证集上比最优轮差了近一倍。改进方向按性价比排序：

1. **加 best-checkpoint**：`copy.deepcopy(model.state_dict())` 跟踪 `dev_loss` 最小的快照，训练结束再 `load_state_dict` 回来（并记录"最优在第几轮"）。
2. 轮数降到 200 以内（表里最低点大多 ≤ 300）。
3. 加 `weight_decay`（1e-4 量级）或 `nn.Dropout`，隐藏层激活也可换 `ReLU` 改善梯度条件。
4. 固定划分随机种子 + 按类别分层划分，并留出 test 集。

# 五、与上一次练习的对照

第一部分是**手写链式法则**：核心新东西是公式 ②③ 的算子局部反向规则 + ④ 的逆序调用链。这一部分是**把求导外包给框架**，核心新东西变成了：

- **边界意识**：autograd 只负责"给定标量 loss，把梯度算出来"；**零梯度、反向调用顺序、参数更新、batch 划分、加权平均、指标口径**全都还是自己的事——本文第三部分的 8 个坑里有 6 个正好落在框架不管的地方。
- **同一套公式的两种写法**：softmax + CE 合并后的合成梯度（预测减标签）之所以能这么干净，正是因为框架把"逐元素门 + 链式法则"这些中间步骤藏起来了；不先按第一部分手推一遍，就没法判断框架算出来的东西对不对。
- **从"能不能收敛"到"该在哪里停"**：第一部分纠结的是初始化与学习率是否让 GD 走得动（欠优化）；这一部分 Adam 让它轻松走到 `train_loss = 0`，问题立刻反转成**过拟合与早停**——优化太好，反而暴露了泛化问题。

  三个跨练习通用的教训：**① 维度/轴的对齐**（第一部分的 `sum(dim=0)` ↔ 这一部分的"乘 batch size"）；**② 结构性的括号 / 返回错张量**（BCE 的括号 ↔ `return a1`）；**③ notebook 的旧输出会骗人**——第一部分是缓存了改前的报错，这一部分是旧的 `Dev_score` 曲线让人以为模型在正常学习。
