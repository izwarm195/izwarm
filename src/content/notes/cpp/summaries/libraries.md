### **第 49 节：Using Libraries in C++ (Static Linking)**

Cherno 首先阐述了他的项目哲学：**克隆仓库就能直接编译运行**，不需要任何包管理器或额外下载。因此他倾向于把依赖库的二进制文件直接放在项目文件夹里。

**库的两大组成部分**

每个 C++ 库通常包含两个目录：

- **`include/`**：头文件，提供函数声明（告诉编译器有哪些函数可用）
- **`lib/`**：预编译的二进制文件，提供函数定义（让链接器找到实际实现）

**静态链接 vs 动态链接**

- **静态链接**：库的代码被直接**嵌入到可执行文件**中，发布的 EXE 自带一切
- **动态链接**：库在**运行时**才被加载，EXE 旁边需要额外的 DLL 文件

Cherno 明确偏好在可能的情况下使用静态链接，原因有两个：一是链接时优化（LTO）可以产出更快的代码；二是分发简单，不需要附带额外的 DLL。

**Visual Studio 配置步骤（以 GLFW 为例）**

1. 将依赖文件放入 `dependencies/GLFW/` 目录，包含 `include/` 和 `lib/`
2. 在项目属性 → **C/C++ → 常规 → 附加包含目录** 中，用 `$(SolutionDir)dependencies\GLFW\include` 指定头文件路径
3. 在项目属性 → **链接器 → 常规 → 附加库目录** 中，用 `$(SolutionDir)dependencies\GLFW\lib` 指定库文件路径
4. 在项目属性 → **链接器 → 输入 → 附加依赖项** 中，填入具体的 `.lib` 文件名

关键在于使用 `$(SolutionDir)` 宏来保持路径的相对性，确保代码在不同机器上都能编译。

**"unresolved external symbol" 错误**

Cherno 花了不小的篇幅解释这个经典错误：编译器只负责确认函数**声明**存在（通过头文件），链接器才负责找到函数**定义**。如果你头文件配好了但库没链接，编译器静默通过，链接时才会爆出 "unresolved external symbol"。他还演示了手动写一个函数定义来消除这个错误，以此证明问题出在缺少库的定义上。

**C 库与 `extern "C"`**

如果链接的是 C 语言编写的库（如 GLFW 实际上是 C 库），需要用 `extern "C"` 包裹声明，防止 C++ 的名称修饰（name mangling）导致链接失败。

### **第 50 节：Using Dynamic Libraries in C++**

这节是第 49 节的延续，专门讲解动态链接。

**动态链接的两种方式**

1. **编译时已知依赖**：通过 `dll.lib` 文件（导入库），在编译期让链接器知道函数的入口点，运行时自动加载对应的 `.dll`
2. **运行时任意加载**：使用 `LoadLibrary`（Windows API）在运行时动态加载 DLL，然后从中提取函数指针来调用。这种方式不需要事先知道库里有什么。

**关键细节**

- `dll.lib` 和 `.dll` 必须**配对使用**，否则函数的内存地址对不上，调用时会崩溃
- 运行时常见的 "DLL not found" 错误本质上就是动态库依赖没有被满足。最简单的解决办法就是把 `.dll` 文件放在 EXE 同级目录下

**静态与动态的对比总结**

| 方面 | 静态链接 | 动态链接 |
|---|---|---|
| 链接时机 | 编译时 | 运行时 |
| EXE 大小 | 较大（库嵌入其中） | 较小（库独立） |
| 分发方式 | 单个 EXE | EXE + DLL |
| 优化空间 | 更高（LTO 可行） | 有限 |
| 更新库 | 需重新编译 | 替换 DLL 即可 |

### **第 51 节：Making and Working with Libraries in C++ (Multiple Projects in Visual Studio)**

这是三节课中最实操的一节。Cherno 手把手演示如何在 Visual Studio 中创建一个包含多个项目的解决方案：一个可执行项目（`Game`）和一个静态库项目（`Engine`），让引擎项目被游戏项目链接使用。

**项目结构**

```
Game.sln
├── Game/          (配置类型: Application .exe)
│   └── src/
│       └── Application.cpp
└── Engine/        (配置类型: Static Library .lib)
    └── src/
        ├── Engine.h
        └── Engine.cpp
```

**配置步骤**

1. 创建 `Game` 项目后，右键解决方案 → 添加 → 新建项目 → `Engine`
2. 把 `Engine` 的**配置类型**设为"静态库(.lib)"，`Game` 保持"应用程序(.exe)"
3. 在 `Game` 的属性中，C/C++ → 常规 → 附加包含目录，用 `$(SolutionDir)Engine\src` 指向引擎的头文件目录
4. **引用是关键**：右键 `Game` → 添加 → 引用 → 勾选 `Engine`。这一操作同时完成了三件事：
   - 自动链接 `Engine.lib`
   - 建立依赖关系（构建 `Game` 时自动先构建 `Engine`）
   - 库改名时无需手动修改链接器设置

**头文件引用的约定**

Cherno 提到了 `#include` 使用双引号 `""` 和尖括号 `<>` 的个人习惯：

- 用**双引号**引用该解决方案内的、自己编写的文件（如 `"Engine.h"`）
- 用**尖括号**引用外部依赖或标准库（如 `<GLFW/glfw3.h>`）

实际上两者编译行为几乎没区别，这更多是一种代码可读性和语义区分上的实践。

**效果验证**

构建并运行后，`Game.exe` 可以正常调用 `Engine::PrintMessage()`，且最终的输出目录里只有一个 `Game.exe`——因为引擎是静态链接进去的。Cherno 还演示了把 EXE 单独复制到桌面上运行，证明没有任何外部依赖。
